# Changelog

## [Unreleased]

### Fixed

- **`Scry.Document.Executor.run/3` silently miscounted an ordinary `GROUP BY` query with no `PARENT`/`SIBLINGS`/`ANCESTORS` at all** -- found building `scry_graph`'s own, structurally identical executor, not caught by this package's own original test suite. Any query with no pseudo item unconditionally routed through the per-row marker/projection path meant for resolving pseudo-fields, which can only ever see one row at a time -- `GROUP BY category { category, count: count(category) }` over two same-category rows returned `count: 1`, not `2`, since `Scry.Core.QueryOps.run_flat/3` never saw both rows together. Fixed by delegating wholesale to `run_flat/3` (unmodified query included) whenever the top-level select has no pseudo items at all; the marker/per-row path now only ever runs when one is actually present, where it was already correct (a pseudo-field alongside `GROUP BY` is, and remains, an explicit `{:error, {:unsupported, :pseudo_field_with_group_by}}` rather than either miscounting or guessing). New regression test in `test/scry/document/executor_test.exs`.

### Added

- Initial project scaffold: `mix.exs` (app `:scry_document`, `{:scry_core, path: "../scry_core"}` + direct `ichor`/`ichor_runtime` dependencies since this package does its own grammar parsing/analysis/dispatch, matching `scry_time_series`'s own precedent), `.credo.exs`/`.formatter.exs`/`.tool-versions`, `AGENTS.md`/`CLAUDE.md`.
- `priv/grammar.aether`: fills **two** of core's extension points at once -- `select_ep1a` (lang_spec.md §8.3's `DEEP`, a bare EP1(a) header modifier with no arguments, unlike `LAST`) and `body_item_ep1` (`PARENT`/`SIBLINGS`/`ANCESTORS`, an EP1(c) "scoped pseudo-field" shape -- the XPath `parent::`/sibling-axis/`ancestor::` equivalents). The EP1(c) shape had only ever been exercised by a fixture fragment in `scry_core`'s own test suite before this package (`Scry.Core.GrammarComposeTest`'s `@graph_like_fragment`, standing in for `scry_graph`'s own `VIA`) -- this is the first real, shipped package to fill it for real.
- `Scry.Document.Grammar.compile/0`: merges this fragment with core's own unanalyzed grammar (`Scry.Core.Grammar.compile_unanalyzed/0` + `Scry.Core.GrammarCompose.merge/2`) -- the same shape `scry_time_series`'s own identical function already established.
- `Scry.Document.Actions`: owns `select_ep1a` (tags the result the bare atom `:deep`, not a payload tuple, since `DEEP` takes no arguments), `body_item_ep1`/`parent_field`/`siblings_field`/`ancestors_field` (each tags `{:parent, body}`/`{:siblings, body}`/`{:ancestors, body}` -- core's own `body_item` handler already wraps this one level further as `{:variant, ...}` automatically, confirmed by reading it directly, not assumed), and delegates every other rule/token to `Scry.Core.Actions`, the same delegation-not-composition shape and `FunctionClauseError`-module-check fallback `scry_time_series`'s own identical module already established.
- `priv/gen/generate_compiled_grammar.exs`: produces the checked-in `Scry.Document.Grammar.Compiled`, mirroring `scry_time_series`'s own generator exactly.
- `Scry.Document.parse/1`: mirrors `Scry.Core.parse/1`'s own shape, using the merged grammar and `Scry.Document.Actions`.
- **`Scry.Document.Conn`** -- a reference document tree, reusing the exact `%{[String.t(), ...] => [row]}` shape every existing engine's own `conn` already has (`Scry.Engine.InMemory.Conn`, e.g.), the only change being that keys may now have more than one segment, with segment order encoding tree position (a filesystem-path convention: `["a", "b"]` is the parent of `["a", "b", "c"]`). Not a new storage primitive -- found, before writing this, that no existing engine or shared test fixture supports a real multi-segment source at all (two of the four real adapters `[table] = source`-pattern-match and would `MatchError` on one today; `scry_core`'s own `TypeCheck`/`Introspection` explicitly treat a multi-segment source as unmatchable).
- **`Scry.Document.Executor.run/3`** -- real execution for `DEEP`/`PARENT`/`SIBLINGS`/`ANCESTORS`, taking a `Scry.Document.Conn.t()` directly rather than dispatching through `Scry.Core.EngineBehaviour`: confirmed no existing behaviour callback receives the whole keyed document space these constructs all need (`DEEP` searches across every stored key for a depth-agnostic match; `PARENT`/`SIBLINGS`/`ANCESTORS` resolve *other* keys relative to a row's own key), unlike `LAST`, which only ever needs the row already in hand and so could stay a pure AST-rewrite-then-delegate-to-any-engine pass. `DEEP`'s own semantics (XPath `//`, confirmed directly with this repo's own maintainer, since lang_spec.md's own "recursive descent, vs. one child level" phrase names no worked example or concrete mechanics) match a source's first+last segment at any depth between (or just the last segment, for a single-segment source). Ordinary `WHERE`/`ORDER BY`/`LIMIT`/`OFFSET`/plain-field projection are not reimplemented -- delegated to `Scry.Core.QueryOps.run_flat/3`, the same toolkit every other engine reuses, via a synthetic per-row correlation field threaded through and stripped back out before any real result is returned.
  Explicit scope limits, returned as clear errors rather than undefined behavior: a pseudo-field combined with `GROUP BY` (`{:error, {:unsupported, :pseudo_field_with_group_by}}` -- an aggregated row no longer corresponds to one specific document node, and neither spec says what that combination should mean) and `%Scry.Core.CombinedQuery{}` (`{:error, {:unsupported, :combined_query}}` -- not this round's focal capability). Nesting one pseudo-field inside another (`PARENT { PARENT { category } }`) wraps rather than flattening (`%{"parent" => %{"parent" => %{"category" => ...}}}`) -- a deliberate, documented reading of an otherwise-open question (neither spec states an expected output shape), following the same "a pseudo-field is an ordinary named body item, nothing special-cases its own nesting" rule uniformly.
- `test/scry/document_test.exs`/`test/scry/document/grammar_parity_test.exs`: grammar/parse coverage for all four keywords, mirroring `scry_time_series`'s own equivalent files; confirms (and documents as a known, unfixed `scry_core` scope gap, not something papered over) that `Scry.Core.TypeCheck`'s own category check catches `DEEP` on a `relational`/`olap`-tagged source exactly like `LAST` already does, but does **not** catch `PARENT`/`SIBLINGS`/`ANCESTORS` on the same, since the check only ever inspects `query.variant`, never `query.select`'s own `{:variant, ...}`-tagged body items.
- `test/scry/document/executor_test.exs`: real execution coverage, including the `lang_spec.md` §8.3 worked example (`library.catalog.shelves.shelf.books.book`, `WHERE`/`LIMIT`, nested `PARENT`, `ANCESTORS`) run for real against a hand-built `Scry.Document.Conn` fixture matching that example's own shape, not just traced by hand.
